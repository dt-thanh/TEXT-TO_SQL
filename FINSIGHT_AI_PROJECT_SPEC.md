# 1. Project Summary

## 1.1 Project name

**FinSight AI**

## 1.2 One-sentence description

FinSight AI is a **Financial Market & Risk Intelligence Platform** that ingests real financial market and macroeconomic data into a Snowflake analytics warehouse, transforms it with dbt, and provides an AI-powered natural-language analytics interface that generates, validates, executes, explains, and displays SQL transparently to the user.

## 1.3 Core idea

The product is **not simply a Text-to-SQL chatbot**.

Text-to-SQL is one capability inside a larger system:

```text
Financial data sources
        ↓
Data ingestion
        ↓
Data warehouse
        ↓
Analytics marts
        ↓
Semantic/business layer
        ↓
Natural language question
        ↓
SQL generation
        ↓
SQL validation
        ↓
SQL execution
        ↓
Result analysis
        ↓
Table + chart + explanation + generated SQL
```

The main goal is to reduce the time required for a financial analyst to move from:

```text
Business question
→ finding data
→ preparing data
→ writing SQL
→ validating results
→ visualizing findings
→ interpreting results
```

to:

```text
Business question
→ FinSight AI
→ transparent SQL
→ trusted result
→ insight
```

# 2. Business Problem

## 2.1 Target users

Primary personas:

- Financial Analyst
- Market Risk Analyst
- Treasury Analyst
- Data Analyst in a financial institution
- Investment/Research Analyst

Secondary personas may be added later.

## 2.2 Current pain point

Financial analysis often requires data from multiple sources.

Example:

A user wants to answer:

> "How did BTC perform when US Treasury yields were increasing?"

Without FinSight, the workflow may be:

```text
Find crypto market data
        ↓
Find Treasury yield data
        ↓
Download / call APIs
        ↓
Clean both datasets
        ↓
Normalize dates
        ↓
Join the datasets
        ↓
Write SQL/Python
        ↓
Calculate returns / volatility
        ↓
Visualize
        ↓
Interpret
```

This creates several problems:

1. Business users may not know SQL.
2. Analysts repeatedly write similar queries.
3. Data from different sources may use different frequencies and time semantics.
4. Incorrect joins can create misleading results.
5. SQL generated by an LLM can be unsafe or logically wrong.
6. A traditional chatbot may hide its SQL and therefore reduce user trust.
7. A dashboard usually answers predefined questions but is weak for ad-hoc investigation.

## 2.3 Product value

FinSight AI provides:

- centralized financial data;
- repeatable data pipelines;
- governed analytics marts;
- business definitions for financial metrics;
- self-service natural-language analytics;
- visible SQL for transparency;
- SQL explanation for learning and auditability;
- safe query execution;
- structured evaluation of generated SQL.

# 3. Product Principles

The following principles are mandatory unless explicitly changed.

## 3.1 SQL must remain visible

Generated SQL is a first-class product feature.

The UI should show:

1. natural-language answer;
2. visualization;
3. result table;
4. generated SQL;
5. SQL explanation.

Example:

```text
Question:
"Compare BTC and ETH volatility when the 10Y Treasury yield was above 4%."

Answer:
...

Chart:
...

Data:
...

Generated SQL:
...

How this SQL works:
1. Filter days where Treasury yield > 4%.
2. Select BTC and ETH.
3. Aggregate volatility by symbol.
4. Compare the two assets.
```

## 3.2 Data engineering is a core part of the product

Do not treat the database as a static demo dataset.

The project must demonstrate:

- ingestion;
- historical backfill;
- incremental loading;
- scheduling;
- data quality;
- transformations;
- dimensional/data-mart modeling;
- time alignment;
- lineage;
- testing.

## 3.3 The LLM must not query raw data directly

The preferred path is:

```text
RAW
→ STAGING
→ CORE
→ MART
→ AI layer
```

The Text-to-SQL agent should primarily query curated MART models.

## 3.4 Do not add technology without a clear problem

Examples:

- Kafka is not added just because it is popular.
- Spark is not added just to make the architecture look bigger.
- A vector database is not added unless retrieval scale requires it.
- Kubernetes is not part of the MVP.

Every technology must solve an identified technical or business problem.

## 3.5 Preserve point-in-time correctness

Financial and macroeconomic data have time semantics.

A value must not be used before it was actually available to the analyst.

This is especially important for monthly macro data such as CPI.

# 12. Time Semantics

This section is critical.

The following time fields are **not interchangeable**.

## 12.1 Binance `open_time`

Meaning:

> Exact timestamp when a crypto candle starts.

Example:

```text
2026-09-19 08:00:00 UTC
```

## 12.2 `trade_date`

Meaning:

> Calendar date used for market-level daily analysis.

Derived from Binance timestamps.

## 12.3 FRED `observation_date`

Meaning:

> Period that the macroeconomic observation describes.

Example:

A CPI value may describe August.

## 12.4 `realtime_start` / `available_date`

Meaning:

> Date from which that information was available/known.

This prevents look-ahead bias.

# 13. Daily vs Monthly Data

Binance may be hourly.

FRED indicators may be:

```text
daily
monthly
quarterly
```

Do not force all raw data into daily frequency.

## 13.1 Daily FRED series

Example:

```text
DGS10
```

Crypto exists every day, including weekends.

Macro observations may not.

For missing days:

```text
Use last known macro observation
```

But preserve metadata:

```text
source_date
is_carried_forward
days_since_observation
```

This makes it clear that the value was carried forward.

## 13.2 Monthly FRED series

Example:

```text
CPIAUCSL
```

Do **not** do this:

```text
August CPI
→ assign to every day in August
```

if the August CPI was only published later.

That creates look-ahead bias.

Preferred approach:

```text
DIM_DATE
        ↓
as-of join
        ↓
latest macro value actually available on each date
```

Concept:

```text
For date X:
select latest valid observation
whose available_date <= X
```

This point-in-time logic should eventually be implemented in dbt.

Airflow is responsible for orchestration, not business logic.

Recommended DAG flow:

```text

        ↓

        ↓
load_binance_raw
        ↓

extract_fred
        ↓
validate_fred_raw
        ↓
load_fred_raw
        ↓

dbt_run_staging
        ↓
dbt_run_core
        ↓

        ↓

```

Prefer business logic in reusable Python modules/dbt models instead of embedding large logic directly inside DAG code.

# 22. SQL Generation Rules

Generated SQL must:

- be readable;
- use explicit columns;
- prefer curated marts;
- qualify table names;
- use CTEs when logic becomes complex;
- avoid unnecessary `SELECT *`;
- have an appropriate result limit for exploratory queries;
- follow Snowflake SQL syntax;
- avoid DDL/DML;
- avoid uncontrolled cross joins;
- not invent tables or columns.

---

# 23. SQL Guard

Use `sqlglot` to parse generated SQL.

Allowed:

```text
SELECT
WITH
JOIN
GROUP BY
ORDER BY
CTE
WINDOW FUNCTIONS
```

Blocked:

```text
DROP
DELETE
UPDATE
INSERT
TRUNCATE
ALTER
CREATE
MERGE
```

Additional controls:

```text
table allowlist
schema allowlist
maximum result rows
query timeout
query cost protection where possible
```

The LLM must never decide authorization rules by itself.


# 37. Current Product Narrative

When explaining the project to another person:

> FinSight AI is a financial analytics platform built on real market and macroeconomic data. Binance provides crypto market behavior, while FRED provides the macroeconomic environment. The data is ingested through Python and Airflow, stored in Snowflake, and transformed by dbt into clean analytical marts. On top of this data platform, FinSight uses an LLM-based Text-to-SQL agent to let analysts ask questions in natural language. The system retrieves the relevant schema and financial definitions, generates Snowflake SQL, validates the SQL using safety rules, executes it, and returns a table, chart, natural-language explanation, and the exact SQL used. Transparency and SQL visibility are core product features.

# 40. Questions an Agent Must Ask Before Major Changes

Before making a major architecture change, a coding agent should verify:

```text
Does this change solve an existing documented problem?

Does it change the data grain?

Does it change a primary/unique key?

Does it change time semantics?

Does it create look-ahead bias?

Does it change a business metric definition?

Does it introduce a new dependency?

Does it duplicate an existing service?

Does it expose RAW data directly to the LLM?

Does it weaken SQL safety?

Does it break existing API contracts?

Does it require a migration?

Does it require updating evaluation data?
```

If the answer is unclear, stop and document the uncertainty before coding.
